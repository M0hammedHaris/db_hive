## Health Endpoint Contract

This contract provides a concrete JSON schema and CI assertion for Acceptance Criteria #3.

- Path: `GET /health`
- Success condition (CI assertion): HTTP 200 and JSON body with `status === "ok"` and `services.db === "ok"`.
- Minimal response schema (examples):

  {
    "status": "ok",           // "ok" | "degraded" | "fail"
    "version": "v0.1",       // optional service version string
    "uptime": 12345,           // seconds
    "services": {
      "db": "ok"             // "ok" | "fail"
    },
    "timestamp": "2025-10-12T12:00:00Z"
  }

Source note: architecture mandates a JSON metadata/status payload for health checks and basic infra checks (db reachable, env OK). [Source: docs/architecture.md#Deployment, canary & rollback strategy]

CI example assertion (concept):

```bash
# Shell-style example for CI health check
curl -sSf "$CANARY_URL/health" | jq -e '.status == "ok" and .services.db == "ok"'
```

If the assertion fails the CI job must fail and block canary promotion.

## CI Workflow Blueprint

Create a CI workflow at `.github/workflows/canary.yml` with the following logical jobs (names are suggestions):

- `install-and-test` — checkout code, install dependencies, run unit tests (fail fast if tests fail).
- `build` — produce production build artifacts for frontend and backend.
- `deploy:frontend-canary` — deploy frontend build to Vercel canary route (requires `VERCEL_TOKEN` and project identifiers).
- `deploy:backend-canary` — deploy backend serverless functions to chosen provider (Vercel serverless or AWS Lambda; requires CI deploy credentials).
- `canary:health-check` — hit the staging canary URL and run the Health Endpoint Contract assertion; fail the workflow if health-check fails.
- `promote-or-halt` — on success, mark CI job as passed and optionally create a promotion PR or perform automated promotion per policy; on failure, fail and require manual investigation.

Notes:

- Use `ubuntu-latest` runners and standard actions: `actions/checkout`, `actions/setup-node`, caching steps for package manager, and provider-specific deployment actions.
- Replace test/build commands with the project's package manager commands (e.g., `npm ci && npm test && npm run build`).
- Store all deploy tokens and secrets in GitHub Actions secrets or the chosen secret store; do NOT commit tokens to the repo.

## Testing frameworks & file paths (implementation suggestions)

- Unit tests: use the project's chosen unit test runner for Node/TS (e.g., Jest) and place tests under `backend/tests/unit/**` and `frontend/tests/unit/**`.
- E2E tests (canary path): use Playwright and place tests under `tests/e2e/canary/**` that run the end-to-end canary flow in staging.
- Example minimal health unit test location: `backend/tests/unit/health.test.(ts|js)` asserting the `/health` route handler returns the contract above.

## Canary promotion / rollback guidance

- If the `canary:health-check` job fails, the workflow MUST fail and block promotion. Recommended actions on failure:
  - Stop automated promotion and alert the on-call / release owner.
  - Optionally toggle feature flags to disable new UI flows (if feature flags are in place).
  - If automatic rollback is enabled, the CI may trigger a rollback job that redeploys the previous stable artifacts; otherwise require manual rollback procedure by the release manager.
- Document the chosen promotion/rollback policy in `docs/DEPLOY.md` (see Task 4.2).
